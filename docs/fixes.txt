SiftPipe — Fixes Log

Real bugs found and fixed across the project's development, one session
per dated entry. Kept for the historical record of what broke and why —
verification/test-count narration and "not yet done" status notes have
been trimmed throughout, since the deployed app is the current source of
truth for what works. Provider-specific details that no longer apply
(the pipeline used Groq through SESSION 8; SESSION 9 migrated it fully to
Anthropic) are noted as historical rather than restated as live
constraints.


================================================================================
SESSION 1 — First real end-to-end pipeline run (2026-07-30)
================================================================================

1.1 validated_payloads.json was a placeholder, not a real B6 curation
    B6's entire design is "human filters B5's payloads down into
    validated_payloads.json" — that step had never actually been
    performed; the file was a hardcoded 1-target/3-payload stub. Rebuilt
    it for real from B5's actual output (37 payload executions across 5
    real targets instead of 3), no code changed.

1.2 B9's vulnerability-label matching could never produce a Hybrid match
    correlate_results.py matched B3 (static) and B7/B8 (dynamic) findings
    by exact string equality on "vulnerability". B7 emits underscored
    labels ("Command_Injection"); B3 emits spaced ones ("Injection") —
    never string-equal, so the "Hybrid (Static + Dynamic)"/CONFIRMED
    branch was dead code. Fixed with _normalize_vuln_label() (lowercase,
    underscores to spaces) plus a substring check, so a narrow dynamic
    label can match a broader static category the way the two scanners
    actually categorize things. This is a label-matching fix, not a
    leniency change — a dynamic finding still needs an independent
    "confirmed" classification from B8 to reach Hybrid/CONFIRMED.

1.3 B8 had no resilience against an exhausted daily token budget
    ask_llm() catches every exception and returns a fake finding
    ({"vulnerability": "API Error", ...}); B8 called the LLM once per B7
    finding with no memory of prior runs, so hitting the (then-Groq)
    daily cap mid-run turned every remaining payload into a bogus
    placeholder, and a re-run burned tokens again on already-classified
    payloads. Fixed with two independent changes to B8's loop, both still
    in the code today regardless of provider: (a) reuse a prior run's
    valid classification instead of re-asking, and (b) skip the LLM call
    entirely when B7's own rule-based checks found no anomaly at all —
    a zero-signal finding reliably classifies as discarded anyway, so
    this stops paying for a foregone conclusion. Measured effect at the
    time: ~30% fewer real LLM calls needed for a full B8 pass.

Known limitation carried forward: the target app (a stock, unmodified
Mattermost instance) is not actually vulnerable to the classic OWASP
payloads used — most B7/B8 findings are expected to stay
discarded/possible. These fixes address data volume, token cost, and
correlation correctness; they don't and can't manufacture real
vulnerabilities that aren't there.

SESSION 2 — `--mode fresh` debugging (2026-07-31)
================================================================================

1.1 No check that Docker was even running — an uncaught CalledProcessError
    killed the whole pipeline with a raw traceback if Docker Desktop
    wasn't running. Fixed with check_docker_available(), a clear
    RuntimeError up front.

1.2 `docker compose down -v` did not actually reset anything — the stack
    bind-mounts Postgres/Mattermost data to host paths instead of named
    volumes, so `-v` was a no-op. "Fresh" mode silently behaved like
    "restore" at the data layer. Fixed with wipe_volumes(), run inside a
    throwaway Alpine container (sidesteps a Windows PermissionError a
    plain shutil.rmtree() hit, since the container has the same Linux-side
    rights that created the files).

1.3 seed.py assumed an admin account already existed, and silently
    swallowed failures on every call after the first. Fixed with
    create_admin_account() (a fresh, zero-user Mattermost instance
    auto-grants System Admin to the first account created — the same
    bootstrap exception used here deliberately) plus .raise_for_status()
    on every seed request.

1.4 60s boot timeout was too short for a real fresh boot (measured
    101–105s). Raised to 120s.

1.5 Results-folder deletion could hit a transient Windows file lock.
    Added a retry loop.

1.6 run_seed_script() invoked "python" literally instead of
    sys.executable, risking a different interpreter than main.py's own
    venv. Fixed.

fresh_reset() sequencing after these fixes: check_docker_available() ->
docker_down() -> wipe_volumes() -> docker_up() -> wait_for_mattermost() ->
create_admin_account() -> run_seed_script() -> clear_results_folder().

SESSION 3 — B4 resilience + B7 HTTP-capture fix (2026-07-31)
================================================================================

1.1 B4 had hardcoded credentials/team/channel while B7 already read the
    same values from .env. Fixed with the same env-backed config pattern
    B7 already used.

1.2 One uncaught exception anywhere in B4's login->crawl sequence
    silently produced empty, "successful"-looking output — a login
    failure and "genuinely found nothing" were indistinguishable. Fixed:
    every stage now appends a structured {"stage", "message"} entry to an
    `errors` list, and a new _determine_status(login_ok, errors)
    classifies the run as failed/partial/complete instead of a hardcoded
    "complete".

1.3 No resilience to a single transient navigation failure. Added
    _goto_with_retry() (2 attempts, 1s backoff) for login, team creation,
    and each route crawl.

2.1 B7's HTTP response capture rewrite. The old design used one
    persistent page.on("response") listener filtered by a loose substring
    match on the URL, gated by a fixed 2-second sleep — a same-prefix GET
    (Mattermost fires one right after a new post renders) could silently
    overwrite the captured response with an unrelated 200 OK, and a
    server response slower than 2s left status/body empty, indistinguishable
    from "nothing to report". Fixed with Playwright's expect_response(),
    scoped exactly to the submit action, plus a new
    _is_submission_response predicate (POST method + exact URL suffix —
    not a loose substring). A genuine timeout (8s, no matching response)
    now raises and is recorded as an explicit error instead of empty
    fields.

Known limitation carried forward: _is_submission_response() was
Mattermost-API-specific at this point (hardcoded to /api/v4/posts and
/api/v4/commands/execute) — generalized to a target-agnostic predicate in
SESSION 8.

SESSION 4 — Taxonomy-based evaluation engine for B5/B9 (2026-07-31)
================================================================================

Replaced B9's free-text substring correlation and B5's pure-keyword
target relevance with a formal CWE/OWASP taxonomy, taxonomy-tier matching
with an LLM-judge fallback for ambiguous pairs, and a weighted composite
confidence/severity score instead of a single LLM-assigned label.

1. blocks/taxonomy.py (new) — a curated CWE catalog (scoped to what B3's
   prompt and B7's rule-based detections actually cover, not the full CWE
   catalog) plus the OWASP Top 10 category list. infer_taxonomy(finding)
   resolves {cwe_id, owasp_category} in priority order: an explicit
   cwe_id already on the finding, an explicit category with no CWE, or a
   free-text label lookup as a legacy fallback.

   Found and fixed while building this: static_scanner.py's OWASP
   category codes didn't match the real numbering (Injection tagged
   wrong, Security Misconfiguration tagged wrong) — every B3 finding had
   been emitting the wrong category code. Corrected, and corrected again
   the same day once it became clear the pipeline should target OWASP Top
   10:2025 rather than 2021 (finalized January 2026) — see the addendum
   below.

2. blocks/scoring.py (new) — compute_score(static_confidence,
   dynamic_result, dynamic_confidence, match_tier) -> (score in [0,1],
   severity). Weighted composite: dynamic evidence 0.50, static evidence
   0.25, correlation match tier 0.25 — weighted toward dynamic evidence
   deliberately, since a live-proven exploitation attempt is stronger
   signal than a static heuristic guess.

3. B3 — cwe_id added to the existing LLM call's JSON schema (no new call,
   no added cost).

4. B7 — cwe_id/owasp_category derived deterministically from the
   already-computed rule-based `vuln` label, no LLM call.

5. B9 — the actual evaluation engine rewrite. Matching tried in priority
   order per dynamic finding: "cwe" (exact CWE match, deterministic),
   "judge" (same OWASP category, different/missing CWE — one capped,
   cached LLM call decides if they're the same issue), "owasp" (same
   category, judge unavailable/inconclusive), "text" (legacy substring,
   only when neither side has any taxonomy). Judge verdicts are cached
   per (payload, static file, candidate) key and reused across runs, and
   new judge calls are capped per run to protect the LLM API budget on a
   run with many ambiguous pairs. Every correlated entry gained cwe_id,
   owasp_category, match_tier, score, and severity, additive to the
   existing fields. Static-only findings (no dynamic counterpart) also
   get a score via a dedicated "untested" weight, instead of a hardcoded
   "MEDIUM" string with nothing backing it.

6. B5 — the best-matching related static finding's taxonomy is surfaced
   to the LLM as a prompt hint and attached to the output, so a generated
   payload set can be traced back to a specific CWE, not just a free-text
   rationale.

Known limitations carried forward: the curated CWE catalog is a subset,
not the full standard — a class outside it correlates via the "text"
tier; the weighted-score formula (0.50/0.25/0.25) is a reasoned starting
point, not empirically tuned against a labeled dataset; B5's relevance
ranking is still keyword-overlap, not taxonomy-driven — the taxonomy tag
rides on whatever that search already returns.

SESSION 4 ADDENDUM — OWASP Top 10 2021 -> 2025 correction (2026-07-31)
--------------------------------------------------------------------------------

Everything in SESSION 4 above was built against OWASP Top 10:2021, then
corrected the same day once it was confirmed that OWASP Top 10:2025 (final
January 2026) was already the current edition. blocks/taxonomy.py and
blocks/static_scanner.py's category codes were re-keyed to the real 2025
numbering (Injection A03->A05, Security Misconfiguration A05->A02, Broken
Access Control and Authentication Failures unchanged at A01/A07; two new
2025 categories — Software Supply Chain Failures and Mishandling of
Exceptional Conditions — added as placeholder catalog entries, since
nothing in the pipeline generates findings for either yet). All test
fixtures referencing the old codes were updated to match.

SESSION 5 — Wire the React UI to the real backend + build the B6 approval UI
(2026-08-01)
================================================================================

Before this session, only Sidebar.tsx talked to the real backend —
PipelineView/CorrelationView/LogsView all rendered static mock arrays, and
B6 (human review) had no UI at all beyond a console prompt or a raw curl.

1.1 Sidebar.tsx's active-phase highlighting had never worked —
    BLOCK_TO_PHASE mapped to values that were never real ids on either

    `current_block.toLowerCase()`.

    only worked because mock data happened to reuse the same strings for

2.1 ui/src/lib/types.ts, api.ts, queries.ts (new) — every backend
    response shape transcribed field-by-field from the actual Python

    per concern, one queryKeys object so repeated calls dedupe.

2.2–2.5 Tag/FindingRow/Section decoupled from the old mock shapes;
    ui/src/components/secpipeline/mappers.ts (new) — one pure function
    per source block translating its real shape into a shared UIFinding

    data instead of static arrays.

2.6 PayloadReviewView.tsx (new) — the B6 approval UI. One card per
    payload group with a checkbox per index, select-all/none, an
    optional comment, and a submit button calling POST /api/validate.
    Auto-switches into view the moment the pipeline starts waiting for
    human review.

2.7 data.ts cleanup — removed the mock sections/findings/logLines data
    and their types entirely, now fully superseded by lib/types.ts +

SESSION 6 — Three real bugs found from user-submitted screenshots
(2026-08-01)
================================================================================

1.1 mattermost-src/mattermost (B3's scan target) was an orphaned,
    never-initialized git submodule — no .gitmodules file existed, so it
    had 0 files on disk. B3 "ran successfully" against nothing, with
    {"total_scanned": 0, "findings": []} indistinguishable from a real
    empty result. The originally pinned commit turned out to be
    unrecoverable (confirmed via the GitHub API in both candidate
    upstream repos). Fixed by cloning the submodule fresh at the
    `v11.7.0` tag — chosen to match the Docker container's own Mattermost
    version, which the original setup never actually guaranteed.

1.2 Moving the project out of OneDrive left the Windows ReadOnly
    attribute set on almost every folder in the repo — surfaced as what
    looked like an auth error on "Reset environment", actually a
    PermissionError on the final rmdir of an already-emptied, still
    ReadOnly-flagged directory (a known OneDrive side effect, not fixable
    by a retry loop alone since it isn't a transient lock). Cleared the
    attribute recursively as a one-time fix; clear_results_folder() also
    got a wider retry margin and a clearer error message pointing at the
    real possible causes.

1.3 Sidebar.tsx had no concept of "phase already completed" — even after
    SESSION 5's active-phase fix, a fully completed run and a
    never-started one rendered identically (empty circles), since
    current_block resets to null once the pipeline finishes. Fixed with a
    phaseState(index) helper distinguishing done/active/pending by
    position relative to the active phase.

Also fixed along the way: B7's browser.close() was only called once at
the very end of the payload loop with no try/finally — any mid-loop
exception could leave a visible, unclosed Chromium window holding file
handles on just-written screenshots. Wrapped in try/finally.

SESSION 7 — Landing-page automation, B9 rationale, B6 comment persistence
(2026-08-06)
================================================================================

1.1 B4/B7 required manually clicking through Mattermost's "View in
    Browser" interstitial on every run. Traced the real mechanism in the
    Mattermost submodule source: a new session redirects to /landing
    unless localStorage already has a specific flag set true. Fixed by
    setting that flag via an init script on every browser context B4/B7
    create — mirrors Mattermost's own intended mechanism instead of
    scripting a click on the link.

1.2 B9 already computed an LLM-judge rationale for ambiguous matches but
    discarded it before it reached the correlated finding — and the other
    three match tiers had no explanation at all. Fixed: find_match() now
    returns the rationale too, and a new _explain_match() builds a
    one/two-sentence explanation for every tier (cwe/judge cite the exact
    static finding's file:line; owasp/text explain the weaker basis for
    the match; "none" says so plainly). Every correlated entry now
    carries match_rationale and matched_static_finding. No new LLM calls
    — the judge tier reuses a rationale already being computed and
    discarded; the other tiers are template text.

1.3 B6's reviewer comment was accepted by the API and stored only in
    memory — api.py's write of validated_payloads.json never included it,
    so it vanished the moment the run ended. Fixed by writing it to disk
    alongside the payloads; run_history's existing snapshot mechanism
    picked it up automatically, surfacing it in both the live review view
    and Past Runs with no further changes needed.

Frontend: rows with a rationale (B9 only) became click-to-expand, showing
the explanation inline with no new tab/modal.

SESSION 7 ADDENDUM — a rate-limited LLM call left a finding without a
required field, and it crashed the frontend (2026-08-06)
--------------------------------------------------------------------------------

Found live: opening Correlation, or a run under Past Runs, crashed to the
app's global error page. B8's per-finding LLM-call code already
setdefault()s several fields onto whatever ask_llm() returns, but not
`result` — and ask_llm() catches every exception (the specific trigger
here was hitting the then-Groq daily token cap mid-run) and returns a
placeholder with no `result` key at all. The frontend's mapB8Finding()
calls `f.result.toUpperCase()` with no guard, since the type declares
`result` as required. Fixed with `llm_result.setdefault("result",
"discarded")` — "discarded" chosen deliberately as the least consequential
bucket, and the "API Error" label already excludes the entry from being
reused as a valid prior classification. The 4 already-broken entries in
the live results file and one historical run snapshot were patched
directly, since the code fix alone doesn't repair already-persisted data.

The specific trigger (a Groq rate limit) predates the SESSION 9 migration
to Anthropic, but the underlying gap — an LLM-call wrapper's error
placeholder not satisfying its own downstream type contract — and the fix
for it remain in the code today regardless of provider.

SESSION 8 — Multi-target support: NaViQ as a second real target
(2026-08-08 to 2026-08-10)
================================================================================

Generalized the pipeline from a single hardcoded Mattermost target to
also support NaViQ, a second real, authorized local instance, via a
per-target profile system (a closed set of 2 known profiles — see
MULTI_TARGET_PLAN.md's "Non-goals" for why this deliberately isn't a
general "any user adds any site" product). Full phase-by-phase detail is
compiled in docs/siftpipe-compiled.md; this is the condensed bug/fix
record.

Real bugs found live, not by code review alone:

1.1 B7's selector-building treated NaViQ's "no id" sentinel field value
    as a real id, building the unmatchable selector "#unknown" — nearly
    every NaViQ field lacks a real id, so this made B7 close to
    non-functional against it. Fixed by guarding both the id and name
    sentinels.

1.2 B5 captured every form field unconditionally, including hidden ones
    — barely mattered for Mattermost, but NaViQ's CSRF/language-switcher
    hidden fields appear on every page and crowded out the real,
    interesting targets. Fixed by skipping hidden fields.

1.3 NaViQ's contact form has a spam honeypot kept off-screen via CSS +
    aria-hidden rather than type="hidden" — Playwright's own is_visible()
    doesn't catch that, so a naive auto-fill-sibling-fields feature (added
    the same session to stop an unrelated required field from blocking
    submission) would have filled it and gotten every payload flagged as
    bot traffic. Fixed by also skipping aria-hidden fields.

1.4 XSS_reflected false-positives on non-XSS payloads and JSON responses
    — found by checking real historical run data, not code review. SQLi/
    command-injection test payloads got tagged XSS purely for being
    echoed back verbatim, since Mattermost's own chat API always returns
    your post in its JSON response. Fixed with two required gates: the
    payload must contain real HTML/JS syntax, and the response must
    actually look like HTML, not JSON.

1.5 B3 had never actually run against NaViQ — its extension/directory
    filter was tuned entirely to Mattermost's Go/TypeScript stack, and its
    file-list cache had no target in its name, so whichever target ran
    first won the cache forever. Fixed with per-target scan
    configuration and a target-scoped cache filename.

1.6 The A02 hardcoded-secret prompt flagged a correct env-var read as a
    literal secret, and separately the LLM was emitting "not found"
    placeholder entries instead of an empty array despite the prompt
    forbidding it — several were saved as real findings before this was
    caught. Fixed both in the prompt and with a code-level backstop
    (reject any finding with no real cited line number).

1.7 Building NaViQ dev-server automation (needed so a juror can run the
    whole pipeline from the frontend with no terminal) surfaced three
    bugs: the server's own log file lived under results/ and collided
    with every reset's wipe; a leaked file descriptor; and — the
    significant one — the "Run analysis" button could enable while the
    database was still mid-reset, found only via live testing that
    sampled the button's state across an entire real reset window.

1.8 Every block wrote a single fixed results/{block}.json regardless of
    active target, so running two targets back to back silently
    overwrote one target's output with the other's — confirmed live, not
    theoretical. Fixed with one shared result_path() helper, target-scoped
    filenames threaded through every block, and the same treatment for
    B7's per-target screenshot/video directories. run_history's own
    finish_run() needed a matching fix — it globbed every JSON file in
    results/ regardless of which run/target it belonged to.

1.9 Past Runs silently dropped the target field the backend already sent,
    because the frontend type never declared it.

SESSION 9 — Groq → Anthropic migration (2026-08-19)
================================================================================

Groq decommissioned the `llama-3.3-70b-versatile` model every LLM call in
the pipeline used (B3, B5, B8, B9). Before writing any migration code,
the two highest-judgment prompts (B3 static analysis, B8 dynamic
classification) were tested head-to-head in the Anthropic Console
Playground against `claude-haiku-4-5-20251001` and `claude-sonnet-5`
using real project data. Both models returned equivalent results on both
tests, at meaningfully different cost (Haiku roughly half of Sonnet's on
the B8 test) — so the mixed Haiku/Sonnet split originally considered was
dropped in favor of Haiku for all four blocks: simpler code, lower cost,
no quality gap observed. This is the model the pipeline uses today.

Real platform-level finding, not a SiftPipe bug: `claude-sonnet-5` fully
rejects `temperature`/`top_p`/`top_k` (400 error) in favor of an adaptive
`effort` parameter — doesn't affect the shipped code (Haiku still accepts
`temperature=0.0`), but matters if a block is ever routed to Sonnet
later, since that call site would need `effort=` instead.

Migration: `requirements.txt`'s `groq` dependency swapped for
`anthropic`; every `ask_llm()` implementation (main.py/blocks/pipeline.py
for B3/B8/B9, blocks/generate_payloads.py for B5) swapped
`client.chat.completions.create()` for `client.messages.create()`, with
`system` moved to a top-level parameter and `max_tokens` now required
explicitly. The existing markdown-fence-stripping and JSON-parse-fallback
logic was left untouched. B8 and B9 needed zero changes themselves, since
both receive `ask_llm` as a parameter rather than importing a client
directly. Stale "Groq quota"/"Groq" comments elsewhere in the codebase
were updated to reflect the new provider.

Caveat carried forward: the Haiku-vs-Sonnet validation above tested
"doesn't hallucinate a finding on a clean file," not "matches Sonnet's
detection recall on a file with a real vulnerability" — accepted
consciously given the very small cost delta actually observed, not
independently re-verified since.

SESSION 10 — B10: per-run PDF report, CWE-grounded B9 judge,
POSSIBLE-finding explanations, CWE-grouped Recommendations (2026-08-19)
================================================================================

Round 1 — B10 base:

blocks/report.py (new) renders one run's already-computed, already-
persisted B9 output into a bilingual PDF via headless Chromium printing
(for real per-physical-page numbering) — deliberately zero new LLM calls,
since a report re-judging evidence on every export would be
non-reproducible and would burn budget for no analytical value. CONFIRMED
or HIGH-severity findings get a full narrative card (evidence, screenshot
if one still exists on disk — screenshot files aren't namespaced by run,
so a later run of the same target can overwrite an earlier one's; the
report shows a plain "no longer available" note rather than a broken
image). `GET /api/runs/{id}/report?lang=en|es` serves it; PastRunsView
gained a download menu.

blocks/taxonomy.py's CWE_CATALOG gained a real MITRE-sourced description
per curated CWE — the B9 judge's prompt now grounds its reasoning in real
reference text for both sides of an ambiguous pair, not just two free-text
labels; the same field feeds the report's CWE appendix.

Explicitly declined this round, with reasoning: a live-translate widget
for the Spanish PDF (no browser tab exists at generation time, and a
generic MT engine shouldn't be trusted with classification terminology);
a full CWE knowledge-base/RAG system (a ~16-entry static dict is the
right scope, not infrastructure); CVE-database integration (a different
feature — SiftPipe detects CWE/OWASP patterns in first-party code, not
known CVEs in named dependencies); an LLM-generated report narrative
(same non-reproducibility reasoning as the report's overall design).

Round 2 — closing a real gap in Round 1: POSSIBLE findings (the majority
of what B9 typically produces) were dumped into a bare table with no
explanation, and repeated findings of the same root cause showed as N
unrelated rows.

Every POSSIBLE finding not already promoted to a full card now gets a
compact explanation built only from fields B9 already computed
(evidence, collapsed to one line, plus match_rationale) — no new
analysis generated, a deliberate scoping constraint. A new
"Recommendations" section groups CONFIRMED/POSSIBLE findings by CWE (so
repeated instances of the same weakness collapse into one entry, whether
in the same file or copy-pasted across several) with one authored,
general-guidance remediation line per CWE class, explicitly labeled as a
template rather than a verified fix — nothing in the pipeline computes an
actual suggested fix. The remediation catalog was extended to cover three
CWEs that showed up in real run data but weren't in the original curated
set, rather than leaving them on the generic fallback note.

Confirmed against real correlation data, not just synthetic fixtures:
three same-file findings of the same CWE collapsed into one recommendation
group as designed, and two same-CWE findings in different files also
collapsed into one group, confirming the "group by CWE alone" design
decision behaves correctly on both cases.

Known limitation carried forward: the remediation catalog covers 19 CWEs,
not the full standard — any CWE outside it gets a generic fallback note
rather than a fabricated fix, and the curated set grows only when a real
run surfaces a new CWE outside it. The B9 judge's own rationale text stays
English-only even in the Spanish report — a bounded, accepted gap, not
revisited since.

SESSION 11 — Per-run evidence storage for B7 screenshots/videos
(2026-08-25)
================================================================================

B7's screenshot/video paths were namespaced by target only, so a second
run of the same target overwrote the first run's evidence files on disk
even though the JSON finding data itself was already immune to this —
and both paths lived under results/, which a Fresh Reset wipes wholesale.
Fixed with an evidence_dir(target, run_id) helper — evidence/{target}/
{run_id} — threaded through B7's execution path, served via its own
StaticFiles mount alongside the existing one. B4's own discovery video
keeps the old overwrite-on-rerun behavior on purpose: it isn't referenced
from anywhere persistent, so it's a live debug artifact, not evidence
tied to a specific historical finding.

SESSION 12 — B7: unauthenticated-access probe (broken access control)
(2026-08-25)
================================================================================

B7's only access-control-adjacent rule flagged the presence of a
401/403 — the opposite of real broken access control (a request that
should have been rejected but wasn't). B7 only ever ran through one
authenticated session, so there was no signal at all for "this endpoint
accepts a real submission with zero auth." Fixed: one extra anonymous
probe call per field (a fresh browser context with neither cookies nor
localStorage, covering JWT-in-localStorage targets too), using a benign
probe value so it can't also trip the SQLi/XSS rules. A 2xx response
produces a Broken_Access_Control finding. Deliberately not pre-filtered
against "is this endpoint supposed to be public" — left for B8's
judgment, same as every other rule-based B7 signal.

SESSION 13 — B4/B7: bare GET action-link probe (broken access control)
(2026-08-25)
================================================================================

SESSION 12's auth probe only covers form fields. A real bug found reading
a candidate third target's routes had no form at all — a bare GET on a
numeric-id path (e.g. /consultas/leido/5) with no auth filter, while
every sibling admin route in the same file had one. B4 only discovers
forms/inputs; B7's execution model drives form-fill-and-submit — neither
had any way to notice a bare link like that exists.

Fixed: blocks/crawler.py gained a check for this specific route shape (a
purely-numeric path segment — deliberately path-only, not query-string
aware, since a query parameter would fire on nearly every ordinary
filter/search link) and a matching link-selection function, reusing the
existing crawl's same-origin/denylist filtering. B4 records these
separately during its existing crawl. B7 gained a matching anonymous-GET
check, run once per discovered link at the end of the payload loop,
reading the discovery output directly rather than going through B5/B6

SESSION 14 — B3: numbered source lines so the LLM cites the right one
(2026-09-20)
================================================================================

B3's reported line numbers were unreliable — some off by 20+ against real
NaViQ code. The model was reading raw file text and asked to report a
finding's line, forcing it to count newlines implicitly; LLMs read
tokens, not lines, so the error grows with distance from the top of the
file. Every downstream consumer of "line" (correlation's matched-finding
location, the PDF report's file:line) inherited the wrong number.

Fixed at the source: every line sent to the model is now prefixed with
its real 1-based line number, and the prompt instructs the model to copy
that number rather than count. Live-checked against real NaViQ files with
and without the fix, using "does the cited line actually contain the
quoted evidence" as the metric (independent of whether the finding itself
is a real vulnerability): 0 of 5 cited lines matched without the fix
(off by 8–30 lines); 3 of 3 matched exactly with it.

Not yet done: small sample (3 files with findings, one run each) — not
established whether the fix changes detection rate as opposed to just
citation accuracy; one file's numbered-prompt run returned no findings
