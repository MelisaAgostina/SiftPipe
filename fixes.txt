SiftPipe — Fixes Log (first real end-to-end pipeline run)
Date: 2026-07-30

This documents the problems found running the pipeline B3→B9 end to end for
the first time, and the fixes applied. Scope was deliberately kept narrow:
B7 (dynamic_injector.py) and B8/B9's core analysis logic were left alone
unless a fix was structurally necessary; most of the value came from fixing
DATA (validated_payloads.json) rather than code.


1. PROBLEMS OBSERVED
---------------------

1.1 validated_payloads.json was a placeholder, not a real B6 curation
    results/validated_payloads.json contained a hardcoded 1-target/3-payload
    "smoke-test" stub. human_review.py's entire design (B6) is "human filters
    B5_payloads.json down into validated_payloads.json" — that step had never
    actually been performed. Result: B7 only ever executed 3 payloads against
    1 target, so B8 had almost nothing to analyze and B9 had almost no
    dynamic data to correlate.

1.2 B9's vulnerability-label matching could never produce a Hybrid match
    correlate_results.py matched B3 (static) and B8 (dynamic) findings by
    exact string equality on the "vulnerability" field. B7 emits underscored
    labels (e.g. "Broken_Access_Control", "Command_Injection"), while B3's
    static scanner emits spaced labels (e.g. "Broken Access Control",
    "Injection"). These could never be string-equal, so the
    "Hybrid (Static + Dynamic)" / CONFIRMED branch in B9 was effectively
    dead code — B9 could only ever report "Dynamic" or "Estático" sources,
    regardless of how good the underlying data was.

1.3 B8 had no resilience against Groq's daily token cap
    ask_llm() in main.py catches every exception (including HTTP 429 rate
    limit errors) and returns a fake finding: {"vulnerability": "API Error",
    "evidence": str(e)}. analyze_results() (B8) called the LLM once per B7
    finding with no memory of prior runs. Once the free-tier daily cap
    (100,000 tokens/day) was hit mid-run, every remaining payload silently
    became a bogus "API Error" pseudo-finding in results/B8_dynamic.json,
    and a naive re-run would burn tokens again on payloads that had already
    been classified successfully before the cap was hit.


2. FIXES APPLIED
-----------------

2.1 Curated validated_payloads.json from B5's real output (data only)
    Rebuilt results/validated_payloads.json from results/B5_payloads.json:
      - Dropped all fileUploadInput entries — dynamic_injector.py already
        hard-skips these (set_input_files isn't implemented), so keeping
        them was dead weight.
      - Grouped remaining entries by (page_url, field_id) and de-duplicated
        payload variants, since B5 had generated multiple overlapping
        "form field" / "input" entries for the same real page.
    Result: 5 targets, all backed by real forms B4 (dynamic_analysis.py)
    actually discovered in attack_surface.json (town-square, canal-analisis,
    off-topic, the DM channel, search) — 37 total payload executions instead
    of 3. No code in B7/B8/B9 was touched for this fix.

2.2 correlate_results.py — normalized vulnerability-label matching
    Added _normalize_vuln_label(value): lowercases the string and replaces
    underscores with spaces before comparison. The match condition changed
    from strict equality (b3_vuln == vuln_type) to:
        b3_vuln == norm_vuln_type OR b3_vuln in norm_vuln_type OR norm_vuln_type in b3_vuln
    (both sides normalized), keeping the existing OWASP-category substring
    check as a secondary path.

    Why this shape: the substring check (not just equality) lets a narrow
    dynamic label like "Command_Injection" match a broader static category
    like "Injection", which mirrors how the two scanners actually categorize
    things (B7 is specific per-payload, B3 is a general OWASP bucket).

    Technical implication: this is a label-matching fix, not a leniency
    change to scoring. A dynamic finding still has to be independently
    classified "confirmed" by the LLM in B8 to reach the Hybrid/CONFIRMED
    branch in B9 — this fix only removes a spelling/format mismatch that was
    silently preventing that branch from ever being reachable. Verified with
    a synthetic case: B3 "Injection" + B8 "Command_Injection"/confirmed now
    correctly produces source "Hybrid (Static + Dynamic)", classification
    "CONFIRMED" (previously: "Dynamic" / "POSSIBLE").

    Known side effect (not fixed, by request): correlate_results() always
    writes results/B9_correlation.json to disk, even when called for a test
    or with synthetic pipeline_results. Running tests/test_correlate_results.py
    will overwrite the real B9 output; re-run B9 against real B3/B8 data
    afterward if you need it back.

2.3 analyze_results.py (B8) — resumable analysis + heuristic pre-filter
    Two independent changes to the per-finding loop:

    (a) Resume support
        Before the loop, load any existing results/B8_dynamic.json and index
        it by payload_id. If a payload already has a usable prior result
        (result in {confirmed, possible, discarded} AND vulnerability not in
        {"API Error", "Error de Parseo JSON"}), reuse that entry instead of
        calling the LLM again.
        Why: without this, every re-run re-spent tokens on payloads that had
        already been classified successfully before a rate limit was hit,
        making recovery from a partial run strictly worse over time.

    (b) Skip the LLM when B7 found nothing
        If a finding has anomaly_detected == false (none of B7's own
        rule-based checks fired — no SQL error string, no reflected payload,
        no shell error marker, no 401/403, etc.), skip the LLM call entirely
        and record it locally as {"result": "discarded", "confidence": "low",
        "evidence": "No rule-based anomaly detected by B7; LLM call skipped."}.
        Why: a finding with zero heuristic signal is, in practice, always
        going to come back "discarded" from the LLM anyway — this was
        confirmed against the one real historical case where this played out
        (payload 1_3, anomaly-free, LLM independently said "discarded").
        Skipping doesn't change the outcome, it just stops paying for a
        foregone conclusion.

    Measured effect on the current 37-payload validated_payloads.json:
        - B7 flags 27/37 findings as anomalous (anomaly_detected: true).
        - Of those, 1 already had a valid prior result (reused, 0 tokens).
        - Net: a full B8 run needs 26 real LLM calls instead of 37 (~30%
          reduction), and after any partial rate-limit failure, only the
          still-unresolved payloads are retried — not the whole batch.
        Verified by running analyze_results() with a mock ask_llm() and
        confirming the call counts (llm_calls=26, reused=1,
        skipped_no_anomaly=10) matched the prediction exactly.

    Explicitly NOT done: no retry/backoff loop for 429s. Groq's cap is
    tokens-per-day, not tokens-per-minute — the error messages observed gave
    6-13 minute wait estimates per request, so a short backoff loop would
    not have helped and would have just made a run hang. If a run still hits
    the cap mid-batch, the affected payloads are written as
    "vulnerability": "API Error" (as before) and are safe to retry on the
    next analyze_results() call — they are correctly NOT treated as "usable"
    prior results, so they'll be retried for real, not silently skipped.

2.4 tests/test_correlate_results.py (new)
    Added stdlib unittest tests (chose unittest over pytest: pytest isn't
    installed in the project's .venv and there's no requirements.txt yet, so
    this avoids introducing a new dependency for one test file). Covers:
      - _normalize_vuln_label() directly (underscore→space, lowercasing,
        non-string input).
      - Three correlation outcomes end to end: Hybrid/CONFIRMED match,
        Dynamic-only POSSIBLE (no static match), Static false-positive
        (discarded dynamic result that does match a static finding).
    Run with: python -m unittest tests/test_correlate_results.py -v
    Note: this will overwrite results/B9_correlation.json as a side effect
    (see 2.2) — re-run B9 for real afterward if needed.


3. KNOWN LIMITATIONS / NOT FIXED
----------------------------------

- Groq's 100k tokens/day free-tier cap is an external constraint. The B8
  changes reduce consumption but don't remove the ceiling — a large enough
  validated_payloads.json can still exhaust it in one run.
- correlate_results() writes results/B9_correlation.json unconditionally,
  with no way to redirect output (e.g. for isolated test runs). Left as-is
  per direction given during this session.
- The target app (a stock, unmodified Mattermost instance) is not actually
  vulnerable to the classic OWASP payloads used (XSS/SQLi/command
  injection/path traversal). Most B7/B8 findings are expected to stay
  "discarded" or "possible" (via B7's reflected-payload heuristic, which is
  a byproduct of Mattermost's API normally echoing posted message content
  back in its JSON response — not a real vulnerability). These fixes address
  data volume, token cost, and correlation correctness; they do not and
  cannot manufacture real vulnerabilities that aren't there.

SESSION 2 — --mode fresh debugging (2026-07-31)
================================================================================

Scope: `python main.py --mode fresh` had never been verified to actually
work. The user reported it failing on a prior run. This session isolated
fresh_reset() (blocks/environment.py) from the rest of the pipeline, found
every bug blocking it, fixed them, and verified a real end-to-end run
against a live Mattermost/Postgres stack via Docker Desktop.


1. PROBLEMS OBSERVED
---------------------

1.1 No check that Docker was even running
    docker_down()/docker_up() called subprocess.run(..., check=True) with no
    try/except. If Docker Desktop isn't running (confirmed to be the case at
    the start of this session via `docker info`), this throws an uncaught
    CalledProcessError and kills the whole pipeline with a raw traceback —
    almost certainly what happened on the reported failed run.

1.2 `docker compose down -v` did not actually reset anything
    mattermost/docker-compose.yml bind-mounts Postgres/Mattermost data to
    host paths (./volumes/db, ./volumes/app per mattermost/.env) instead of
    declaring named volumes in a top-level `volumes:` section. `-v` only
    removes named volumes, so it was a no-op here — confirmed by finding
    mattermost/volumes/{app,db} already populated with a prior run's data.
    Net effect: "fresh" mode silently behaved like "restore" at the data
    layer — same admin, same seeded users, same channel/team — while
    claiming ("full wipe" in the docstring) to reset everything.

1.3 seed.py assumed an admin account already existed
    A side effect of 1.2: because the DB was never actually wiped, seed.py's
    login as MM_ADMIN_EMAIL/MM_ADMIN_PASS kept working by accident. Once the
    wipe in 2.2/2.3 below made resets real, a genuinely fresh Mattermost
    instance has zero accounts — there's no admin to log in as, and no API
    endpoint to create one before any account exists (self-registration is
    normally gated by EnableOpenServer, confirmed False in this instance's
    saved config).

1.4 seed.py silently swallowed failures
    Only the initial login call had .raise_for_status(). User/team/channel/
    membership/post creation calls were unchecked — if any of them failed
    (e.g. "already exists" from 1.2's stale data), the corresponding *_id
    became None, later calls failed or no-opped silently, and the script
    still printed "Seed script finalizado con éxito" regardless.

1.5 60s boot timeout too short for a real fresh boot
    wait_for_mattermost()'s default READY_TIMEOUT was 60s. A real fresh boot
    (new Postgres, DB migrations from scratch) measured 101-105s across two
    live runs in this session — comfortably over the old limit.

1.6 Volume wipe hit PermissionError on Windows
    Found while testing the fix for 1.2: Postgres writes its bind-mounted
    data files with Linux ownership/permissions. Under Docker Desktop on
    Windows, a plain Python shutil.rmtree() on those paths from the host
    raises PermissionError ([WinError 5] Access is denied) partway through —
    the host user's Windows account doesn't have rights to remove them
    directly.

1.7 results/ folder deletion hit a transient Windows file lock
    Also found during live testing: shutil.rmtree("results") intermittently
    raised PermissionError on the top-level directory itself (contents
    already deleted) — consistent with a brief handle held by VS Code's file
    watcher (results/ was open in the editor during the test run) or a
    similar indexer. Not reproducible on every run.

1.8 run_seed_script() invoked "python" literally
    subprocess.run(["python", "seed.py"]) instead of using sys.executable —
    could silently pick a different interpreter than the one running
    main.py (e.g. missing requests/dotenv) depending on PATH, independent of
    which venv main.py itself was launched from.


2. FIXES APPLIED (all in blocks/environment.py unless noted)
--------------------------------------------------------------

2.1 check_docker_available()  — new
    Runs `docker info` up front; raises a clear RuntimeError ("Docker
    daemon not reachable. Start Docker Desktop...") instead of letting a
    deep subprocess call crash with a raw traceback. Also wrapped
    docker_down()/docker_up() themselves in try/except CalledProcessError
    for the same reason (e.g. compose file errors, port conflicts).

2.2 wipe_volumes()  — new
    Explicitly deletes mattermost/volumes/db and mattermost/volumes/app
    after `docker compose down -v`, since -v alone does nothing for this
    stack's bind mounts (see 1.2).

2.3 wipe_volumes() runs the delete inside a throwaway Alpine container
    `docker run --rm -v <abs path to mattermost/volumes>:/target alpine sh
    -c "rm -rf /target/db /target/app"` instead of Python's shutil.rmtree
    on the host — sidesteps 1.6 because the container has the same
    Linux-side rights that created the files in the first place. Verified
    working after the fix (previously crashed with WinError 5 on the first
    live test).

2.4 create_admin_account()  — new
    POSTs to /api/v4/users (unauthenticated) with MM_ADMIN_EMAIL/
    MM_ADMIN_PASS/MM_ADMIN_USERNAME (defaults to "admin") right after
    Mattermost responds to ping. On a zero-user instance this is
    automatically granted System Admin by Mattermost itself — a bootstrap
    exception that exists specifically so a fresh instance doesn't need a
    human at the setup wizard. Verifies the account actually works with a
    real login call afterward (not just a 201 status) before continuing.
    Falls back to wait_for_admin_setup() (a new input()-based prompt, same
    pattern as human_review.py's B6 pause) only if the automated call
    fails for any reason — e.g. a Mattermost instance where the bootstrap
    exception has been disabled at the org level.

2.5 READY_TIMEOUT raised from 60s to 120s
    Based on the 101-105s measured boot times in this session's live runs
    (see 1.5). Still configurable via the function's timeout parameter.

2.6 clear_results_folder() — retry loop added
    Retries shutil.rmtree() up to 5 times with a 1s delay on PermissionError
    before giving up, to absorb the transient Windows lock from 1.7 instead
    of crashing the very last step of an otherwise-successful fresh reset.

2.7 run_seed_script() now uses sys.executable instead of "python"
    Fixes 1.8 — guarantees seed.py runs under the exact same interpreter
    (and therefore the exact same installed dependencies) as main.py.

2.8 seed.py — added .raise_for_status() to every request
    User/team/team-membership/channel/channel-membership/post creation
    calls now all check their response status, fixing 1.4. A failure now
    surfaces immediately with the real HTTP error instead of silently
    producing a None id and a false "finalizado con éxito" message.

2.9 fresh_reset() sequencing updated to:
    check_docker_available() -> docker_down() -> wipe_volumes() ->
    docker_up() -> wait_for_mattermost() -> create_admin_account() ->
    run_seed_script() -> clear_results_folder()


3. VERIFICATION
-----------------

Ran fresh_reset() directly (isolated from main.py's B3-B9 blocks, to avoid
burning Groq tokens/time on unrelated stages) against a real Docker Desktop
+ Mattermost + Postgres stack, twice:
  - Run 1: caught the WinError 5 in wipe_volumes() (fix 2.3 applied
    afterward) and confirmed the admin-creation/seed/timeout fixes all
    worked on the same run (admin created and verified, seed.py completed
    all 7 steps, Mattermost took 104.8s to boot).
  - Run 2 (after 2.3 and 2.6): full sequence completed clean, including the
    volume wipe via container and the results/ retry. Mattermost boot took
    101.2s.


4. KNOWN LIMITATIONS / NOT FIXED
-----------------------------------

- seed.py's subprocess output prints "Seed script finalizado con éxito" as
  mojibake ("con �xito") in the parent console — a console-encoding
  cosmetic issue (not a crash, exit code 0), left as-is; flag if it's worth
  fixing properly (e.g. PYTHONIOENCODING=utf-8 on the subprocess env).
- The API layer (api.py) still has no way to trigger fresh_reset() or
  choose fresh/restore mode at all — /api/run always starts directly at B3.
  Not addressed in this session; next step if/when connecting fresh mode to
  the frontend.
- wait_for_admin_setup()'s manual fallback path uses input(), which only
  works in the console flow. If fresh_reset() is ever called from the API's
  background-thread flow, that fallback would hang; the automated path in
  create_admin_account() should be treated as the only supported path for
  a non-interactive/API context.

SESSION 3 — B4 resilience + B7 HTTP-capture fix (2026-07-31)
================================================================================

Scope: readme.md flagged two known-weak spots — B4 (dynamic_analysis.py) is
"the most fragile point in the pipeline" (hardcoded selectors/routes, no
error reporting), and B7 (dynamic_injector.py) "doesn't robustly capture the
real HTTP response body". Addressed both, code-only (no live Docker/
Mattermost run this session — verified via the existing test suite, now 68
tests, all passing).


1. B4 (blocks/dynamic_analysis.py) — config, retries, real error reporting
--------------------------------------------------------------------------

1.1 Problem: hardcoded credentials/team/channel, unlike B7
    discover_attack_surface()'s defaults (base_url, login_id, password) and
    its page_routes list were literal strings ("equipo-tesina",
    "canal-analisis", "usuario_test", "victima@test.com", "Password123!"),
    while dynamic_injector.py (B7) already reads the same values from .env
    (MM_URL/MM_TEAM/MM_USERNAME/MM_PASSWORD). Any change to seed.py's
    fixture data silently broke B4 without a config change to match.

    Fix: added module-level env-backed config (MM_URL, MM_TEAM, MM_CHANNEL,
    MM_USERNAME, MM_PASSWORD, MM_SEED_USERNAME — the last two are new,
    documented in .env), same pattern as B7. page_routes is now built from
    these instead of literals. MM_CHANNEL/MM_SEED_USERNAME added to .env
    with defaults matching seed.py's NEW_CHANNEL/NEW_USER so behavior is
    unchanged unless .env is edited.

1.2 Problem: one uncaught exception anywhere silently produced empty,
    "successful"-looking output
    The whole login -> team-setup -> forms -> per-route crawl sequence lived
    inside one outer try/except that just printed and returned whatever had
    been gathered so far — main.py's run_dynamic_discovery() then always
    wrote {"status": "complete", ...} regardless. A login failure and a
    "discovered nothing because that's genuinely everything" run were
    indistinguishable to the UI.

    Fix: every stage (login, team_setup, forms:dashboard, each route,
    inputs:final_page) now has its own try/except appending a structured
    {"stage": ..., "message": ...} entry to a local `errors` list instead of
    only printing. A new pure helper, _determine_status(login_ok, errors),
    classifies the run as "failed" (login never worked — nothing usable),
    "partial" (login worked, but something along the way didn't), or
    "complete" (no errors at all). attack_surface now carries "status" and
    "errors" keys; main.py's run_dynamic_discovery() now reads
    attack_surface.get("status"/"errors") into the B4_dynamic.json summary
    instead of hardcoding "complete". Covered by 4 new unit tests on
    _determine_status (no browser needed, same rationale as
    build_attack_surface_records).

1.3 Problem: no resilience to a single transient nav failure
    Any one-off network hiccup on a page.goto() call failed that stage
    outright. Added _goto_with_retry() (2 attempts, 1s backoff) and used it
    for the login page load, the create_team flow, and each route crawl.

1.4 Explicitly NOT changed: headless=False
    Considered making headless mode configurable (relevant for a future
    API/UI-triggered run, where a visible Chromium window on the server is
    generally undesirable) but left as-is by request — visibility into the
    live run is wanted for now. Revisit when B4 is actually wired to the API.

    browser.close() is now in a try/finally around the whole login->crawl
    sequence (previously implicit via the outer try/except's fallthrough;
    now guaranteed even if a future change adds an uncaught path).


2. B7 (blocks/dynamic_injector.py) — HTTP response capture rewrite
---------------------------------------------------------------------

2.1 Problem: no correlation between "this payload's submission" and
    "whatever matching response arrived"
    The old design registered ONE page.on("response", ...) listener for the
    whole session, writing into a shared `captured` dict, filtered only by
    `"/api/v4/posts" in response.url or "/api/v4/commands" in response.url`
    — a plain substring check with no HTTP-method filter. Mattermost's
    client fires GETs like /api/v4/posts/{id}/thread right after a new post
    renders; those also matched the substring and could silently overwrite
    `captured` with an unrelated 200 OK body instead of the actual
    submission's response (which is what would carry SQL error strings,
    reflected payload content, stack traces, etc.).

2.2 Problem: capture was gated on a fixed 2-second sleep, not a real
    synchronization point
    _execute_one() pressed Enter, slept 2000ms, then checked whatever was in
    `captured`. A server response slower than 2s left status_code/
    response_body empty — visually identical to "request submitted cleanly,
    nothing to report", when it actually meant "we stopped watching before
    the answer came back". This is the concrete mechanism behind the
    readme's "no captura de forma robusta el cuerpo HTTP real" note.

2.3 Fix: page.expect_response() scoped to the submit action
    Replaced the persistent listener + shared dict with Playwright's
    expect_response() context manager, entered right around
    page.keyboard.press("Enter"). New pure predicate _is_submission_response
    checks response.request.method == "POST" AND the URL (right-stripped of
    a trailing slash) ends exactly with "/api/v4/posts" or
    "/api/v4/commands/execute" — no longer a loose substring match, so a
    same-prefix GET can't be mistaken for the submission. A genuine timeout
    (8s, no matching response observed) now raises PlaywrightTimeoutError,
    caught explicitly and recorded as
    result["error"] = "No matching POST /api/v4/posts (or /commands/execute)
    response observed within 8s" — a real signal instead of silently empty
    fields. Covered by 5 new unit tests on _is_submission_response (method
    filtering, exact-suffix matching, the /thread false-positive case) plus
    one integration-level test confirming a timeout surfaces as a visible
    error rather than a false "nothing happened".

2.4 Test infrastructure updated to match
    tests/test_dynamic_injector.py's FakePage previously delivered fake
    responses by calling the stored on("response") callback from inside
    wait_for_timeout() — a fake built around the same race this fix removes.
    Replaced with FakeExpectResponse, a context manager stand-in for
    page.expect_response() that hands back the next queued FakeResponse (or
    raises the fake timeout if None was queued), independent of any sleep.
    FakeResponse gained a .request.method attribute so _is_submission_response
    can be exercised for real.


3. VERIFICATION
-----------------

Full suite: `python -m unittest discover -s tests -v` — 68 tests, all
passing (62 before this session + 4 for _determine_status + 6 for
dynamic_injector's new capture logic). No live Docker/Mattermost run this
session; B4's live-boot path was already verified end-to-end in SESSION 2,
and this session's changes to it are additive (config sourcing, error
tracking, retries) rather than a change to the core navigation logic itself.


4. KNOWN LIMITATIONS / NOT FIXED
-----------------------------------

- B4 still opens a visible (headless=False) browser window — fine for local
  runs, will need to become configurable before B4 can be triggered from the
  API/UI without popping a Chromium window on the server (see 1.4).
- B7's 8-second response timeout is a fixed constant, not configurable per
  call. Reasonable for Mattermost's normal post-submission latency, but a
  genuinely slow target could still produce a false "no response observed"
  error.
- _is_submission_response() is Mattermost-API-specific (hardcoded to
  /api/v4/posts and /api/v4/commands/execute). If B7 ever targets a
  different endpoint shape, this predicate needs to grow alongside it.

SESSION 4 — Taxonomy-based evaluation engine for B5/B9 (2026-07-31)
================================================================================

Scope: replace B9's free-text substring correlation and B5's pure-keyword
target relevance with something closer to what real DAST/SAST correlation
engines do — a formal CWE/OWASP taxonomy, taxonomy-tier matching with an
LLM-judge fallback for ambiguous pairs, and a weighted composite confidence/
severity score instead of a single LLM-assigned label. Design was agreed
with the user up front on two axes: (1) correlation = taxonomy matching +
LLM-judge only for ambiguous pairs (not a full LLM-judge cross product, to
respect Groq's 100k tokens/day cap), and (2) findings get a computed
weighted score instead of a bare high/medium/low label.


1. NEW: blocks/taxonomy.py
-----------------------------

Curated CWE catalog (14 entries, scoped to what OWASP_SCOPE in
static_scanner.py actually looks for and what dynamic_injector.py's
rule-based detections actually produce — not an attempt at the full ~900-
entry CWE catalog) + the real OWASP Top 10 2021 category list.

infer_taxonomy(finding) resolves a finding's {cwe_id, owasp_category} in
priority order: (1) an explicit cwe_id already on the finding, (2) an
explicit owasp_category/category with no CWE, (3) a lookup from the
free-text "vulnerability" label via LABEL_TO_CWE — the fallback that keeps
this working for legacy/pre-taxonomy data and test fixtures that don't carry
a cwe_id. This graceful-degradation design is why the 3 pre-existing B9
tests (SESSION 1) kept passing unmodified: their hand-authored fixtures
never had cwe_id, so they exercise tier 3 automatically.

1.1 Found and fixed while building this: static_scanner.py's OWASP_SCOPE
    dict keys didn't match the real OWASP Top 10 2021 numbering — Injection
    was tagged "A05" (should be A03) and Security Misconfiguration was
    tagged "A02" (should be A05). B3 has been emitting the wrong category
    code for every finding it ever produced. Fixed so it lines up with
    taxonomy.py's OWASP_TOP10_2021 table; Broken Access Control (A01) and
    Identification/Authentication Failures (A07) were already correct.


2. NEW: blocks/scoring.py
----------------------------

compute_score(static_confidence, dynamic_result, dynamic_confidence,
match_tier) -> (score in [0,1], severity). Weighted composite: dynamic
evidence 0.50, static evidence 0.25, correlation match tier 0.25 — weighted
toward dynamic evidence deliberately, since a live-proven exploitation
attempt is stronger signal than a static heuristic guess; match tier is a
corroboration multiplier, not the primary signal. Severity buckets
(CRITICAL/HIGH/MEDIUM/LOW) are threshold-based on the score, not another
LLM call. Every weight is a module-level constant, not buried in branching
logic, specifically so the formula is auditable/citable.


3. B3 (static_scanner.py) — cwe_id added to the existing LLM call
----------------------------------------------------------------------

get_analysis_prompt()'s requested JSON schema gained a "cwe_id" field (with
worked examples: CWE-89 for SQLi, CWE-78 for OS Command Injection, etc.) —
same LLM call already being made, no new token cost per file scanned.


4. B7 (dynamic_injector.py) — deterministic taxonomy, no LLM involved
---------------------------------------------------------------------

After computing `vuln` from the rule-based `detections` list (unchanged
logic), each finding now also gets cwe_id/owasp_category via
infer_taxonomy({"vulnerability": vuln}) — free, since B7's detection is
already rule-based/deterministic, not an LLM call.


5. B8 (analyze_results.py) — taxonomy carried through, not re-derived
-----------------------------------------------------------------------

B8 classifies confirmed/possible/discarded; it doesn't decide WHAT the
vulnerability class is — that's B7's rule engine's job. So cwe_id/
owasp_category are read off the incoming B7 finding and setdefault'd onto
the B8 output (in both the no-anomaly-skip path and the real LLM-call
path), rather than asking the classification LLM call to reinvent them.


6. B9 (correlate_results.py) — the actual evaluation engine rewrite
------------------------------------------------------------------------

correlate_results(pipeline_results=None, ask_llm=None) — new optional
ask_llm param (main.py and api.py's call sites updated to pass it through;
existing/test call sites that omit it still work, see 6.4).

Matching is now tried in priority order per dynamic finding, each tier a
stronger signal than the last:
  1. "cwe"   — exact CWE-ID match between both sides. Deterministic, free.
  2. "judge" — same OWASP category but a different/missing CWE ("ambiguous").
               One LLM call decides if they're really the same underlying
               issue: {"same_vulnerability": true|false, "rationale": ...}.
               Only attempted when ask_llm is provided.
  3. "owasp" — same OWASP category, but the judge was unavailable/not
               provided/returned something unparseable — a shared category
               is still real signal on its own, just weaker than a judge "yes".
  4. "text"  — the original substring/category-string matching, reached only
               when neither side has ANY usable taxonomy (keeps the pipeline
               working even against data with no taxonomy info at all).

6.1 Judge calls are resumable and capped
    _load_previous_judgments() reads a "judgments" dict persisted inside
    results/B9_correlation.json (same file, new top-level key) and reuses a
    cached verdict for a given (payload_id, static file, candidate index) key
    instead of re-asking. MAX_JUDGE_CALLS = 15 caps new calls per run — same
    rationale as B3's MAX_FILES=10 and B8's reuse logic: protect Groq's
    100k tokens/day cap on a run with many ambiguous pairs.

6.2 Every correlated entry gained cwe_id, owasp_category, match_tier, score,
    and severity fields, in addition to the existing vulnerability/target/
    classification/confidence/source/evidence fields (additive — nothing
    existing was removed, api.py's /api/results/B9_correlation passthrough
    needs no changes).

6.3 Static-only findings (no dynamic counterpart at all) now also get a
    score via a new "untested" dynamic_result weight (0.3) in scoring.py,
    instead of a hardcoded "MEDIUM" string with nothing backing it. Also
    fixed a pre-existing typo: their classification was "POSIBLE", now
    "POSSIBLE" (matches every other classification value B9 emits).

6.4 Backward compatible by construction, verified: the 3 pre-existing B9
    tests (SESSION 1, exact CWE-less fixtures) still pass unmodified —
    walked through the match_tier logic by hand for each: tier 1 (cwe) never
    fires since none of those fixtures carry a cwe_id, tier 2 (judge) is
    skipped when ask_llm isn't passed and immediately falls through to a
    tier-3 "owasp" match instead, reproducing the exact same match_found
    outcome the old string-matching logic produced for those 3 specific cases.


7. B5 (generate_payloads.py) — targets tagged with taxonomy
----------------------------------------------------------------

After find_related_static_findings() (keyword-overlap logic unchanged — a
full rewrite of relevance ranking was judged out of scope this round), the
best-matching related finding's taxonomy is computed once via
infer_taxonomy() and: (a) surfaced to the LLM as a prompt hint ("Likely
relevant: CWE-89 (OWASP A03) — weight the 5 payloads toward this class"),
using the same LLM call already being made, and (b) attached to the output
item as cwe_id/owasp_category via setdefault(), so B7/B9 can trace a
generated payload set back to a specific CWE instead of only the LLM's
free-text "rationale". Targets with no related static finding get
cwe_id/owasp_category = None (the prompt's existing "cover 5 different
classes generically" instruction still applies for those).

-----------------

Full suite: `python -m unittest discover -s tests -v` — 102 tests, all
passing (68 before this session + 14 for taxonomy.py + 8 for scoring.py +

9. KNOWN LIMITATIONS / NOT FIXED
-----------------------------------

- CWE_CATALOG and LABEL_TO_CWE are a curated ~14-entry subset, not the full
  CWE catalog. A vulnerability class outside this set gets cwe_id=None from
  the label-fallback tier (owasp_category may still resolve if the LLM/rule
  engine provides a category directly) and correlates via the "text" tier.
- The LLM-judge prompt asks for a single yes/no + rationale; it doesn't ask
  the LLM to propose a corrected CWE ID for either side, so a "no" verdict on
  a genuinely-related pair just means "not correlated this run" rather than
  refining the taxonomy data itself.
- find_related_static_findings() in B5 still ranks by keyword overlap, not

- The weighted-score formula in scoring.py (0.50/0.25/0.25 split, the

  A04 Cryptographic Failures       — moved down from A02:2021
  A05 Injection                    — moved down from A03:2021
  A06 Insecure Design              — moved down from A04:2021
  A07 Authentication Failures      — same position, renamed from "Identification
                                      and Authentication Failures"
  A08 Software or Data Integrity Failures — same position, minor rename
  A09 Security Logging and Alerting Failures — same position, minor rename
  A10 Mishandling of Exceptional Conditions — NEW (2021's A09 Logging renamed
                                      and moved to A09 above; SSRF, 2021's A10,

SESSION 6 — Three real bugs found from user-submitted screenshots

Scope: the project had just been moved out of OneDrive to fix a broken venv

1. BUGS FOUND
--------------------------------------------------------------

1.1 mattermost-src/mattermost (B3's scan target) was an orphaned,
    never-initialized git submodule
    `git ls-tree HEAD mattermost-src/` showed a 160000 gitlink entry, but
    there was no .gitmodules file anywhere in the repo — so `git submodule
    update --init` had no URL to resolve and the folder had 0 files on disk.
    blocks/static_scanner.py's scan_and_save_files() walked an empty
    directory and returned an empty list every time, so results/B3_static.json

    unrecoverable: confirmed via the GitHub API that it doesn't exist in

    (both returned 422 "No commit found for SHA").

1.2 Moving the project out of OneDrive left the Windows ReadOnly attribute
    set on almost every folder in the repo
    Reported by the user as an "auth error" when clicking "Reset environment"
    in the UI; the actual exception was `PermissionError: [WinError 5]
    Access is denied: 'results\dynamic'` from clear_results_folder()'s
    shutil.rmtree() call. Confirmed with `Get-Item ... -Force |
    Format-List Attributes` that results/dynamic had `ReadOnly, Directory,
    Archive` set, and a recursive `Get-ChildItem -Attributes ReadOnly
    -Directory` scan showed the same flag on nearly the entire tree (.git,
    blocks, ui, mattermost, tests, __pycache__, ...). This is a known
    side-effect of copying folders out of OneDrive on Windows. rmtree()
    deletes the folder's contents fine, then fails on the final os.rmdir()
    of the (now empty but still ReadOnly-flagged) directory — not a
    transient file handle, so the existing 5-retry/1s-delay loop could never
    have helped regardless of how long it waited.

1.3 Sidebar.tsx (ui/src/components/secpipeline/Sidebar.tsx) had no concept
    of "phase already completed"
    Even after SESSION 5's fix (which made the *active*-phase highlight work
    at all), the component only ever rendered a phase as highlighted when
    `ph.id === activePhaseId`, with a plain empty Circle otherwise. api.py
    resets pipeline_state["current_block"] to null once the pipeline
    finishes (or errors) — see run_pipeline_from_b7()'s success path and both
    blocks' except clauses — so a fully completed run and a never-started one
    rendered identically: 7 empty circles, no indication of what actually
    ran. This is what the user described as "not intuitive with the states

1. PROBLEMS OBSERVED
---------------------

1.1 Landing-page interstitial had no automation anywhere
    grep across the whole codebase for "landing"/"desktop"/"view in browser"
    found nothing in blocks/dynamic_analysis.py or blocks/dynamic_injector.py

    (the "View in Browser" vs. "View in Desktop App" prompt) unless
    localStorage already has BrowserStore.hasSeenLandingPage() (key
    __landingPageSeen__, constants.tsx) set true. Playwright starts every run
    with empty localStorage, so this fired on every single B4/B7 run — which
    is exactly why the user had been clicking it by hand.

1.2 B9's judge rationale was computed then thrown away
    correlate_results.py's judge() already asked the LLM for a one-sentence
    rationale on ambiguous (same-OWASP-category, different-CWE) pairs and
    persisted it in the on-disk `judgments` dict, but find_match() only ever
    returned the yes/no verdict — the rationale never reached the correlated
    finding dict, and the other three match tiers (cwe/owasp/text) had no
    explanation field at all. Confirmed against the real
    results/B9_correlation.json on disk: DESCARTED (false-positive) entries
    carried B7's dynamic `evidence` but nothing describing why they were
    still correlated to a static finding in the first place.

1.3 B6 comment field was write-only

    pipeline_results["B6"] dict, but api.py's write of
    results/validated_payloads.json only included {"status", "payloads"} —
    the comment was never written to disk, so run_history.finish_run()'s
    glob of results/*.json could never pick it up. It vanished the moment
    the run ended; nothing downstream (PastRunsView, PayloadReviewView)
    rendered it either, since the data never survived past the request
    handler.

SESSION 7 ADDENDUM — B8 "API Error" placeholders crashed the frontend
(2026-08-06)
--------------------------------------------------------------------------------

Found live, not by code review: the user reported that opening the
Correlation tab, or opening a run under Past Runs, showed the app's global
error page ("This page didn't load"). Reproduced with a throwaway Playwright
script against the already-running dev server (`ui/`, port 5173) and live
backend (port 8000) — chose this over guessing from source because
`npx tsc --noEmit` had already passed clean for this session's changes, so a
static check wasn't going to explain a runtime crash. `page.on("pageerror")`
caught the real browser exception directly.

ROOT CAUSE (pre-existing, unrelated to this session's three items above):
`blocks/analyze_results.py`'s per-finding LLM-call `try` block already
`setdefault()`s payload_id/target/payload/vulnerability/cwe_id/
owasp_category/confidence/evidence onto whatever `ask_llm()` returns — but
never `result`. `main.py`'s `ask_llm()` catches every exception (including
Groq 429 rate-limit errors) and returns `{"vulnerability": "API Error",
"evidence": str(e)}` with no `result` key at all. A real run in progress
during this session hit Groq's 100k-tokens/day cap
("Used 99471, Requested 643...") on 4 of its 15 B7 findings, so
results/B8_dynamic.json ended up with 4 entries missing `result` entirely.
`ui/src/components/secpipeline/mappers.ts`'s `mapB8Finding()` does
`f.result.toUpperCase()` with no guard — reasonable given `B8Finding.result`
is typed non-optional in lib/types.ts, but the backend wasn't actually
honoring that contract on the error path. `blocks/correlate_results.py` (B9)
was already defensive here (`b8.get("result", b8.get("status", "discarded"))`
in `_normalize_result_label`'s caller), which is why the crash was specific
to B8's own section of CorrelationView/PastRunsView and not B9's.

FIX:
- blocks/analyze_results.py: added `llm_result.setdefault("result",
  "discarded")` alongside the existing confidence/evidence setdefaults, so
  every B8 finding written to disk always has a valid result value, matching
  the type contract instead of relying on downstream consumers to guess.
  "discarded" chosen deliberately: it's the least consequential bucket (won't
  inflate a confirmed-findings count), and the "API Error" vulnerability
  label already marks the entry as not a real classification for every other
  purpose (`_is_llm_result_usable()` already refuses to reuse it on a re-run,
  so it'll be retried for real next time B8 runs, not silently accepted).
- tests/test_analyze_results.py: new
  test_ask_llm_error_placeholder_still_gets_a_valid_result_field, using a
  fake ask_llm that returns exactly main.py's real API-Error shape (no
  result key) and asserting the output result is one of the three valid
  literals.
- Data-only, no code: patched the 4 broken entries directly in the live
  results/B8_dynamic.json (result -> "discarded") so the running UI recovers
  immediately without needing to burn more Groq tokens re-running B8 while
  the daily cap is still exhausted. Also patched the one affected historical
  snapshot in siftpipe_history.db (run_id=4, block_name="B8_dynamic",
  same 4 entries) — run_history.finish_run() snapshots results/*.json
  verbatim at run-completion time, so the code fix and the live-file patch
  alone would NOT have fixed already-persisted Past Runs history; confirmed
  via direct sqlite3 query that run_id 1-3's B8_dynamic snapshots were
  unaffected (predate this bug being triggered) and only run_id 4 needed it.

VERIFICATION: `python -m unittest discover -s tests` — 113 tests, all
passing. Re-ran the Playwright repro after the fix: no console errors,
Correlation renders its B8/B9 sections (including the "API Error" entry,
now tagged DISCARDED) instead of the error boundary; Past Runs -> Run #4
renders its full historical snapshot instead of crashing.

NOT DONE: the underlying Groq 100k-tokens/day cap is still an external
constraint (unchanged since SESSION 1/4) — this fix stops a capped run's
error placeholders from crashing the UI, it doesn't avoid hitting the cap
itself. Any *future* run that hits the same rate limit will still produce
"API Error" placeholders (by design, for the retry-on-next-run mechanism in
_is_llm_result_usable()) — they just won't crash the frontend anymore.
